Serving SFCC sitemaps

The full path a sitemap request takes – routed behind a reverse proxy, resolved on a custom alias, and served (or not) on a fully headless storefront – and the Module "server" not found trap that headless projects hit with plugin_sitemap. Example values (www.site.com, zzzz-001…, Sites-RefArch-Site) are placeholders; swap for your storefront domain, instance host, and site ID.

A headless storefront serves everything from PWA Kit on Managed Runtime (MRT), but the SEO sitemap is still generated and served by the classic B2C storefront on the ecom instance. A reverse proxy sends the handful of sitemap URLs to ecom and leaves everything else on MRT. Two things then have to line up: the proxy must forward the request transparently (same Host, same path) so ecom resolves the clean URL to the right file, and the SiteMap-Google controller must actually load – which is where a fully headless project trips over plugin_sitemap's dependency on the SFRA server module.

How a request is routed

  1. A crawler or browser requests https://www.site.com/<path> – e.g. /sitemap_index.xml.
  2. The reverse proxy – an eCDN rule or edge reverse proxy in front of MRT – inspects the path. Anything that isn't a sitemap goes to PWA Kit MRT for headless SSR.
  3. If the path is a sitemap file (/sitemap_index.xml, /sitemap_<N>.xml, or a custom sitemap such as /sitemap-…-custom.xml), the proxy routes the request to the B2C ecom origin instead – preserving the Host header (www.site.com) and the path. It rewrites nothing; the backend sees the request exactly as a direct hit would.
  4. ecom resolves the clean URL to a controller: on the alias host, /sitemap_index.xml maps to SiteMap-Google with the bare name=sitemap_index.xml – the request Host supplies the host context (see the next section). This /sitemap_index.xml mapping is hidden and automatic, provided by the platform rather than a route you configure.
  5. The SiteMap-Google controller has to load before it can run. This is the fork the headless case exposes: the stock plugin_sitemap controller is an SFRA module that require('server')s at the top of the file. If the server module isn't present (a fully headless storefront), the load throws Module "server" not found and the request 500s. A dependency-free controller loads regardless.
  6. Once loaded, the controller runs the SendGoogleSiteMap pipelet with FileName = name, which streams the stored sitemap file (200) or returns 404 when no file matches (PIPELET_ERROR).
  7. The response flows back through the proxy to the client.

How the name parameter resolves

The stored file is keyed by (effective host) + name. The effective host comes from the request Host when it is a configured storefront alias; otherwise you have to encode the host into name yourself. So the name carries the host prefix if and only if the request Host isn't already that alias:

Request Hostname=Result
instance host
zzzz-001…salesforce.com		www.site.com%2fsitemap_index.xml
(host-prefixed)		✓ 200
alias host
www.site.com		sitemap_index.xml
(bare)		✓ 200 – the clean-URL path
alias host
www.site.com		www.site.com%2fsitemap_index.xml
(host-prefixed)		✗ no matching file

This is why the proxy must leave Host alone. Routing the request to the ecom instance is correct; the subtlety is that the Host header must still carry the storefront alias, not the instance's own hostname. On the alias, the platform prepends the alias host to the bare name the clean URL produced, so it resolves to the generated file. Point Host at the instance's own hostname (not a configured alias) and nothing is prepended – the bare name is used as-is, matches no generated file, and returns 404.

# Clean SEO URL on the storefront alias -> ecom maps it to a BARE-name controller call:
GET https://www.site.com/sitemap_index.xml                          -> 200
  internally -> SiteMap-Google?name=sitemap_index.xml            -> 200

# Same file via the INSTANCE host: no alias context, so name must carry the host:
GET .../SiteMap-Google?name=www.site.com%2fsitemap_index.xml        -> 200

# Host-prefixed name on the ALIAS host double-counts the host -> misses:
GET https://www.site.com/...SiteMap-Google?name=www.site.com%2fsitemap_index.xml  -> no match

# On the instance's own host (not the alias) the clean URL yields a bare name -> no match:
GET https://zzzz-001.dx.commercecloud.salesforce.com/sitemap_index.xml           -> 404

The headless server-module trap

plugin_sitemap is an SFRA cartridge. Its SiteMap.js opens with var server = require('server'); and registers the route the SFRA way. But the server module is not part of app_storefront_base – it's a cousin, shipped separately in the SFRA modules/ upload that sits alongside the cartridges. A fully headless storefront is the acute case: this SiteMap.js may be the only controller in the whole codebase, so the SFRA server framework was never needed and may not be present at all – and require('server') resolves to nothing.

When server can't be resolved, requiring it throws at controller load time, before any of your logic runs:

ScriptingException: Module "server" not found.  (plugin_sitemap/cartridge/controllers/SiteMap.js#3)
The second server error is a red herring. Any unhandled exception is routed to Error-Start. If the project's Error.js also does require('server'), then Error-Start throws the same Module "server" not found while trying to render the error page – so you see two server errors. The real fault is the original unhandled error upstream; fixing Error.js only lets that real message surface, it doesn't fix the cause.

The fix: a dependency-free controller

Don't add server just for this. The server module only provides SFRA middleware and layering (route chains, request/response helpers), none of which SiteMap-Google needs. Instead, replace (not add) plugin_sitemap's SiteMap.js with a dependency-free, standalone controller that exports Google directly and drives the same SendGoogleSiteMap pipelet. With no require('server'), it loads on a fully headless code version.

Full controller – cartridge/controllers/SiteMap.js (dependency-free) 
// cartridge/controllers/SiteMap.js
/**
 * Serves requests for search provider (Google, Yahoo) XML site maps. Reads a
 * given site map and copies it into the request output stream.
 */
function endpoint() {
    var fileName = request.httpParameterMap.name.stringValue;
    var siteMapResult = '500';
    if (fileName) {
        var SendGoogleSiteMapResult = new dw.system.Pipelet('SendGoogleSiteMap').execute({
            FileName: fileName
        });
        if (SendGoogleSiteMapResult.result === PIPELET_ERROR) {
            siteMapResult = '404';
        } else {
            siteMapResult = '200';
        }
    }
    response.setStatus(siteMapResult);
}
endpoint.public = true;
exports.Google = endpoint;
Convert at your own risk. This is a first-party conversion of the SFRA controller, not a supported drop-in – deploy and test it in a sandbox before production. If you also want the platform error page to render on a headless code version, give Error.js the same dependency-free treatment; that's cosmetic and doesn't change root causes.

Notes & gotchas

  • File names. The index is sitemap_index.xml; children are zero-indexed and may carry a type suffix (sitemap_0.xml, sitemap_0-product.xml, …), and custom sitemaps use a hyphenated sitemap-…-custom.xml form. Match the family, e.g. ^/sitemap_index\.xml$, ^/sitemap_\d+.*\.xml$, or ^/sitemap-[\w]*-custom\.xml$.
  • Where to route. Do the sitemap-vs-everything-else split at the edge – an eCDN rule or reverse proxy in front of MRT. Not inside PWA Kit's app/ssr.js: that already runs on MRT behind the proxy, so the request has left the edge. Steer sitemap paths to ecom and leave Host alone.
  • Alias requirement. In Business Manager → Merchant Tools → SEO → Aliases, add an alias matching the storefront domain so generated sitemap URLs use the right host.
  • Replace, don't add. plugin_sitemap already ships the SFRA SiteMap.js; replace that file rather than layering another cartridge that still pulls in server.
  • The BM download isn't the controller path. The Business Manager sitemap download can succeed while the public URL 500s – they exercise different code, so a working download doesn't mean the controller works.
  • Base cartridge without controllers is normal for headless. app_storefront_base may sit in the cartridge path for non-controller resources; it just won't drag in server unless the SFRA modules/ upload is also present.
